# Project evaluation checklist

Score a candidate dataset or paper against this. Work top to bottom and **stop at the first failed killer** — don't score the rest, the project is dead.

Everything in Part A must be verified by **opening the actual files**, not by reading the paper. Three candidates in a row passed on their abstract and failed on their files.

---

## Part A — Killers (any one fails → reject)

| # | Check | Fail condition |
|---|---|---|
| A1 | **Does the data exist and download?** | Needs login, needs an access application (dbGaP, EGA), "available on request", or dead link |
| A2 | **Is the prediction target already a column?** | The label has to be *constructed* by joining, matching, or inferring across sources |
| A3 | **Are the inputs present, not just referenced?** | Sequences/SMILES are accession numbers or compound names needing thousands of lookups |
| A4 | **Are units stated?** | No units column, or units implied and inconsistent |
| A5 | **Is there enough data?** | Under ~1,500 labelled rows, or under ~400 if you only need classification |
| A6 | **Does it fit on the laptop?** | Usable working set over ~5 GB, or requires a GPU for the baseline |
| A7 | **Do the row counts match the paper?** | Paper, API and download disagree and you can't tell which is right |
| A8 | **Where did the label come from?** | The label is itself a model's prediction, or is computed from the features |

**A8 is the subtlest killer.** Two ways it bites:
- **Circularity.** If the labels were generated by another model (GotEnzymes2's predicted kcat values, AlphaFold confidence scores, any "predicted" column), you're distilling that model, not learning biology. Your ceiling is its accuracy and you'll never know where it's wrong.
- **Leakage by construction.** If the label is derived from the features — even partly, even through an intermediate — you'll get a great score that means nothing. Trace every label back to a physical measurement. If you can't, don't use it.

**A2 is the one that catches most bad projects.** Ask it out loud: "would I have to build the thing I'm predicting?" If yes, stop.

## Part B — Model-readiness (score 0–2 each; **need ≥8/12**)

How much work stands between "downloaded" and "a table with features and a label."

| # | Check | 0 | 1 | 2 |
|---|---|---|---|---|
| B1 | Table structure | Many files, unclear keys | Few files, join works | One table |
| B2 | Parses first try | Needs fixing | Minor fixes | Clean csv/tsv/parquet |
| B3 | Label consistency | Different assays/labs, not comparable | Comparable with normalization | Already normalized by authors |
| B4 | Censored values | Many, policy needed | Some, easy to drop | None |
| B5 | Duplicates | Widespread, disagreeing | Present, easy to dedupe | None |
| B6 | Documentation | Guess what columns mean | Partial | Every column documented |

**Rule of thumb:** if download → feature/label table takes more than a day, the project is harder than it looks. Write that cost down now rather than discovering it in week three.

## Part C — Is the question worth asking? (score 0–2 each; **need ≥6/10**)

| # | Check | 0 | 1 | 2 |
|---|---|---|---|---|
| C1 | **Can it produce a useless answer?** | Only interesting if I beat a strong baseline | Mixed | Informative whichever way it resolves |
| C2 | Existing work | Saturated subfield | Several recent models | Little or none on this data/task |
| C3 | Angle | None | Weak | Clear novel / better / diversity / unique-application case |
| C4 | Is the current method slow or expensive? | Already cheap and solved | Somewhat | Manual, lab-based, or costly |
| C5 | Baseline to compare against | None exists | Vague | A published number, or an obvious dummy |

### C2 expanded — the existing-models audit

"Has anyone modelled this?" is not one question. Answer all five, because the answers point in opposite directions:

| | Question | Why it matters |
|---|---|---|
| C2a | **Does a model for this exact task already exist?** Name it. | If three exist, the field is served and marginal gains won't matter |
| C2b | **Are its weights and code actually available?** | A closed or proprietary model (common in pharma papers) means the open problem is still open — that's an opportunity, not a blocker |
| C2c | **What did it score, on what split?** | A strong number on a *random* split is often weak on a proper one. Re-evaluating an existing model honestly is a cheap, legitimate project |
| C2d | **What did its authors name as the unsolved part?** | Usually in the discussion. This is the highest-value sentence in any paper — it's a question somebody competent couldn't answer |
| C2e | **Can I run it as my baseline in an afternoon?** | If yes, huge ROI: you get a real comparison instead of inventing one |

Scoring guide: **0** = several open, reproducible models with strong honest evaluation. **1** = models exist but are closed, use weak splits, or were trained on much smaller data. **2** = no model for this task, or the only ones are proprietary.

A crowded field is not automatically fatal. What kills a project is a crowded field *with* reproducible models *and* honest evaluation already done. Two of three is an opening.

**C1 is the ROI question.** "How does accuracy decay as X gets more distant?" can't fail. "Beat the published AUPRC" usually does. Prefer the first.

## Part D — Does a pretrained backbone fit? (score 0–2 each; **need ≥4/6**)

| # | Check | 0 | 1 | 2 |
|---|---|---|---|---|
| D1 | A named open-weight backbone matches this data type | None | Exists but restricted/unclear | Open weights, downloadable |
| D2 | Freeze-and-head is viable | Needs full fine-tuning | Needs LoRA or a GPU | Cache embeddings once on CPU |
| D3 | Licence | Blocks the use | Non-commercial, acceptable | Permissive |

Backbones that work: **ESM-2** (proteins, small checkpoints on CPU), **ChemBERTa / MolFormer** (molecules), **AlphaGenome** (DNA, non-commercial, `alphagenome-ft` does heads-only), **Nucleotide Transformer / DNABERT-2 / HyenaDNA** (DNA), **scGPT / Geneformer** (single cells), **RNA-FM** (RNA).

Not freeze-and-head: **AlphaFold** is a structure predictor — use its structures as input features instead, and AF3 weights are restricted. **Diffusion generators** (RFdiffusion, ProteinMPNN) need GPUs and far more data.

## Part E — Evaluation is possible and honest

| # | Check |
|---|---|
| E1 | A non-random split exists that prevents leakage (scaffold, sequence-identity cluster, held-out target, held-out study) |
| E2 | Enough groups to hold out — ≥5 clusters/targets/studies with reasonable size |
| E3 | A meaningful dummy baseline can be computed (global mean, per-group mean, majority class) |
| E4 | The noise floor is estimable (replicate measurements, or duplicate disagreement) |
| E5 | **A positive control exists** — a signal already known to be in the data that the model must recover |
| E6 | **Negative controls are runnable** — label shuffling, feature ablation |
| E7 | **A second independent dataset exists for external validation** |
| E8 | **A published number can be reproduced** on some subset |

E4 is underrated: if different labs measuring the same thing disagree by 0.5 log units, no model can beat that, and knowing the ceiling stops you chasing an impossible number.

### E5 — Positive controls

A positive control is a relationship you already know is in the data. If the model can't recover it, the pipeline is broken and every other number is meaningless. Decide these **before** you look at any real result, or you'll rationalize whatever you get.

Pick at least two:

- **A trivially learnable target.** Swap the real label for something derivable from the features (molecular weight from SMILES, sequence length from sequence). The model should nail it. If it can't, your features or plumbing are wrong.
- **A known effect from the literature.** Something textbook the model should rediscover — a class of molecules known to be more potent, a mutation class known to be destabilizing, a substrate known to be slow. Name it in advance.
- **Well-characterized entities held out.** Items with many replicate measurements and a well-established value. These should be your *easiest* predictions; if they're not, something is inverted.
- **Reproduce a published number** on the same subset and split the original authors used (E8). This is the strongest control available, and the cheapest when the original code runs.

### E6 — Negative controls

Equally important, and these catch leakage, which is the failure mode most likely to waste your time:

- **Shuffle the labels** and re-run the whole pipeline. Performance must collapse to the dummy baseline. If a shuffled-label model still scores well, you have leakage or a bug, full stop.
- **Ablate each feature block** (substrate only, enzyme only, conditions only). If one block does nearly all the work, that's your real finding.
- **Replace features with random noise** of the same shape. Should match the dummy.
- **Shuffle within group** rather than globally, to check your grouped CV is actually grouping.

### E7 — External validation

Testing on a second, independently produced dataset is the difference between "my model fits this table" and "my model works." Options, roughly in order of how convincing they are:

| Approach | What it tests | Cost |
|---|---|---|
| **A different database** (train BRENDA, test SABIO-RK) | lab and curation independence | low |
| **A temporal split** (train on pre-2020 publications, test post-2020) | whether it works on genuinely new measurements | very low, if a year column exists |
| **A different organism or species** | whether it generalizes beyond the dominant taxon | low |
| **A held-out assay type or platform** | whether it learned biology or assay artifacts | low |
| **Prospective check** | pick predictions, then search the literature for whether anyone measured them | medium, and the most convincing |

**The temporal split is the best value in this whole checklist.** If the data has a publication year, it costs one line of pandas and directly answers "would this have worked on the measurements that came next?" Score E7 as 2 if a year or source column exists.

## Part G — Integration potential (score 0–2 each; **need ≥4/8** for a high-impact project)

The single best source of genuinely new questions. A dataset alone answers a small question; joined to something large, it can answer a big one.

| # | Check | 0 | 1 | 2 |
|---|---|---|---|---|
| G1 | **Shared identifiers** | Only free-text names | IDs needing resolution | Standard IDs present (UniProt, Ensembl, EC, InChIKey, PDB, taxonomy, genomic coordinates) |
| G2 | **A named large partner dataset exists** | Can't name one | Something plausible | A specific resource, joinable on a specific key |
| G3 | **The join is one-to-one or cleanly one-to-many** | Ambiguous many-to-many | Manageable | Clean |
| G4 | **The combination answers a bigger question than either alone** | Join for its own sake | Marginally better | A question neither dataset could answer |

**G4 is the real test.** Write the combined question as one sentence before scoring. If you can't, the join is decoration.

### Large datasets worth joining to, and their keys

| Resource | What it holds | Join key |
|---|---|---|
| **UniProt** | ~250M protein sequences + annotation | UniProt accession |
| **AlphaFold DB** | 200M+ predicted structures | UniProt accession |
| **PDB** | ~220k experimental structures | PDB ID / UniProt |
| **ChEMBL** | ~2.4M compounds, 20M+ bioactivities | InChIKey / ChEMBL ID |
| **PubChem** | 100M+ compounds, assay results | InChIKey / CID |
| **BRENDA / SABIO-RK / Rhea / KEGG** | enzyme reactions and kinetics | EC number, reaction ID |
| **MaveDB / ProteinGym** | deep mutational scanning landscapes | UniProt + position |
| **Meltome Atlas / FireProtDB** | protein thermostability | UniProt |
| **CAZy / MEROPS / Pfam / InterPro** | enzyme and domain families | UniProt, family ID |
| **GTEx / Human Protein Atlas** | tissue expression | Ensembl gene |
| **Open Targets** | gene–disease–drug evidence | Ensembl gene, ChEMBL |
| **DepMap** | gene dependency across ~1,100 cell lines | gene + cell line |
| **LINCS L1000** | transcriptional response to compounds | InChIKey + cell line |
| **JUMP-CP / Cell Painting** | compound perturbation images | InChIKey |
| **AlphaGenome Atlas** | ~1 PB precomputed variant effects | genomic coordinates + genome build |

Pick partners whose key your data already contains. Never pick one that needs a new identifier mapping built from scratch.

### Joins fail in predictable ways

- **Identifier versioning.** UniProt accessions get deprecated and merged; Ensembl IDs carry version suffixes; genomic coordinates are meaningless without the genome build. Record the release you used.
- **One-to-many explosions.** One gene has many transcripts; one compound has many salt forms; one protein has many PDB entries. Decide the collapse rule before joining, not after.
- **Isoforms and canonical sequences.** The sequence in your dataset may not be the UniProt canonical one.
- **Silent coverage loss.** Always report what fraction of rows survived the join. A join that keeps 30% has quietly changed your dataset into a different one.
- **Species mismatch.** Human-centric resources won't cover your non-model organism, which is often the whole reason the project was interesting.

## Part H — What's systematically missing? (score 0–2 each; **need ≥4/8**)

Every dataset is a record of what somebody chose to measure. The gaps aren't random, and they decide what your model can honestly claim.

| # | Check | 0 | 1 | 2 |
|---|---|---|---|---|
| H1 | **Are negatives present?** | Only successes recorded | Few negatives | Both outcomes systematically reported |
| H2 | **Is coverage broad?** | One lab, species, cell type or population | A few | Diverse sources |
| H3 | **Can you state what the model would actually be claiming?** | Unclear | Roughly | Precisely, in one sentence |
| H4 | **Would the gaps be obvious to a reader?** | Hidden in the data | Partly documented | Explicit in the paper |

**H3 is the test that matters.** Write the honest claim in one sentence before you start. Not "predicts whether macrocyclization helps" but "predicts whether macrocyclization helps *among cases chemists thought promising enough to synthesize and publish*." The second is still useful. The first is overclaiming, and if you can't tell them apart you'll write the first one by accident.

Common invisible gaps: publication bias toward positives, patents recording only what worked, human data skewed to European ancestry, model organisms crowding out everything else, cell lines standing in for tissue, one assay platform dominating.

## Part I — Does anyone care? (score 0–2 each; **need ≥4/8**)

| # | Check | 0 | 1 | 2 |
|---|---|---|---|---|
| I1 | **Can you name who would use this?** | Nobody specific | A vague community | A named group, lab or company |
| I2 | **Would a result change what they do?** | No | Marginally | Yes — it would redirect an experiment or a decision |
| I3 | **Does the metric match the actual decision?** | Reporting R² when they need a yes/no at a threshold | Roughly aligned | Metric is the decision |
| I4 | **Is ML even the right tool?** | A lookup table or simple rule does as well | ML helps somewhat | The mapping is genuinely complex |

**I4 is worth real honesty.** Before modelling, try the dumbest possible thing: a lookup, a single-feature threshold, a per-group average. If that solves it, the project is a one-page note, not a model — and finding that out in an afternoon is a win.

**I3 catches a common waste.** A model with excellent correlation can be useless if the user needs "is this above the cutoff?" and your errors cluster at the cutoff. Decide the decision first, then the metric.

## Part J — Fit and finishability (score 0–2 each; **need ≥6/10**)

The checklist above judges the project. This part judges the project *for you*.

| # | Check | 0 | 1 | 2 |
|---|---|---|---|---|
| J1 | **Will I learn the ML I want to learn?** | All data cleaning, no modelling | Mixed | Real modelling, splits, evaluation, transfer learning |
| J2 | **Can I tell a sensible result from nonsense?** | No domain intuition and nobody to ask | Some | Yes, or I have someone to check with |
| J3 | **Is there a minimum shareable version?** | All-or-nothing | Partly | A useful result exists at every stage |
| J4 | **Is the time budget defined?** | Open-ended | Vague | A stated number of weeks |
| J5 | **Is there a pre-committed kill date?** | No | Informal | A date and a condition, written down |

**J2 is easy to skip and expensive to skip.** If you can't judge whether a predicted value is biologically plausible, you can't catch your own errors. Either pick a domain you can reason about, or line up someone to sanity-check results before you invest weeks.

**J5 deserves a line in NOTES.md on day one.** Write: "If by *date* I don't have *specific thing*, I stop." Sunk cost is the main reason bad projects continue, and a date written before you're attached is the only reliable defence.

**J3 is how you avoid total losses.** Good shape: the cleaned dataset is useful even if the model is mediocre; the data-quality findings are useful even if the dataset is unusable. Both of the dead candidates here produced a real observation despite failing — that's J3 working.

## Scoring

| Part | Threshold |
|---|---|
| A — Killers | All pass, verified in the files |
| B — Model-readiness | ≥8 / 12 |
| C — Worth asking | ≥6 / 10, with the C2 audit answered in full |
| D — Backbone fit | ≥4 / 6 |
| E — Evaluation | E1, E3 and E6 mandatory; at least one of E5/E8, and E7 if any second source exists |
| G — Integration | ≥4 / 8 if you want high impact; optional for a pure learning project |
| H — Missing data | ≥4 / 8, and H3 written out as a sentence |
| I — Does anyone care | ≥4 / 8 |
| J — Fit and finishability | ≥6 / 10, with J5 written in NOTES.md |

**ROI = (C + D + G + I) ÷ effort.** Rank by that, not by impact alone.

Parts A–F and H are about the data and the question. Parts I and J are about whether it's worth *your* time, and they're the ones most often skipped.

Verdict options: **Do it** · **Do it after verifying X** · **Park it** · **Reject, because…**

## Worked examples from real candidates

| Candidate | Outcome | Where it failed |
|---|---|---|
| Macrocycle-DB matched pairs | **Rejected** | A2 and A4. Acyclic counterparts didn't exist (0 of 50,654 molecules lack a ring), so the target had to be constructed. No units column either. Looked excellent on the abstract. |
| nn4dms DMS extrapolation | **Rejected** | Passed A and B easily (756k rows, 31 MB, clean). Failed C2 — MULTI-evolve and METL cover it — and the one anomaly found was a read-depth artifact, not biology. |
| Fish regulatory elements (iFish) | **Parked** | Passed A, strong on C and D. Failed A6/F on size: 40 TB raw, GPU needed, and you'd have to beat a published AUPRC (C1 weak). |
| scCT-DB drug resistance | **Rejected** | A5 in disguise: 6.19M cells looks huge, but the unit is the patient — ~1,142 across 102 drugs. Also failed C2. |
| Ribocentre-aptamer | **Rejected** | A5. 510 sequences. |
| Enzyme kinetics (CatPred/OED) | **Do it after verifying** | Passes A5, C1, D fully. B is only moderate — mixed units, cross-database duplicates, possible ID lookups. Download and count first. |

### The C2 and G audits applied to the enzyme project

**C2a–e:** CatPred and UniKP exist, both open and reproducible, both scoring well — so C2 is a 1, not a 2. But CatPred's authors explicitly name generalization to dissimilar enzyme sequences as the unsolved part (C2d), and CatPred is runnable as a baseline (C2e). That combination is what makes the project viable despite the crowding.

**E5–E8 for the enzyme project:** positive control — predict molecular weight from the substrate SMILES, which must come out near-perfect, plus check that the model recovers the textbook spread in rates across EC classes. Negative control — shuffle kcat labels and confirm collapse to the per-substrate mean. External validation — CatPred's data is assembled from BRENDA and SABIO-RK, so train on one source and test on the other, and if a publication year is present, add a temporal split. E8 — reproduce CatPred's own reported number on their published split before trusting anything else.

**G:** scores well. The data carries UniProt accessions and EC numbers (G1 = 2), which open the door to AlphaFold DB structures, Meltome Atlas thermostability, and CAZy family labels (G2 = 2). The combined question worth asking: *does structural or thermostability context predict catalytic rate better than sequence alone, especially for enzymes unlike anything in training?* That's a question neither dataset answers by itself (G4 = 2).

## The lesson these cost

Every candidate that died, died at Part A, and in every case the paper's description was the reason it looked alive. **Spend the first thirty minutes downloading the file and counting rows.** That's the whole checklist in one sentence.
